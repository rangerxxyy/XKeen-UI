### Повторная проверка DNS и шаблонов

- Путь включения в `DnsPanel.tsx`: диалог предупреждает, что DNS зависит от Mihomo; затем `POST dns` вызывает RCI для очистки DoH и DoT (ошибка отсутствующего компонента допускается), удаления системного списка DNS, добавления IPv4 `br0`, включения `opkg dns-override` и сохранения конфигурации. После RCI backend записывает присланный `config.yaml`; frontend отдельно отправляет Mihomo `PUT configs?force=true`.
- Путь отключения сначала меняет `dns.enable` в Mihomo-конфигурации на `false`, просит Mihomo перезагрузить конфигурацию, после чего вызывает `DELETE dns`, отключающий `opkg dns-override`. Если в running-config обнаружен DNS `br0`, upstream очищает список серверов и устанавливает `77.88.8.8`; прежние системные DNS, списки DoH/DoT и состояние фильтра в этом сценарии не восстанавливаются.
- В проверенных `DnsPanel.tsx` и `backend/src/dns.rs` нет операции выключения DNS-фильтрующего движка Keenetic или фиксации/восстановления его состояния. Это подтверждает отсутствие функции в просмотренной реализации, но не доказывает отсутствие в других версиях проекта.
- Официальная документация Keenetic описывает `no dns-proxy filter engine` как команду отключения DNS-фильтрующего движка; фильтрующие профили и их привязки — отдельные настройки. Одного отключения движка недостаточно, чтобы считать состояние всех назначений сохранённым и восстановленным. См. [справочник CLI KeeneticOS](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/en/cli_manual_kn-1611.pdf) и [руководство по контентной фильтрации](https://support.keenetic.ru/eaeu/extra/kn-1710/ru/24580-internet-safety--content-filtering-.html).
- Переключатель этой функции в XKeen UI не подключать к живому роутеру, пока не реализованы полное чтение и сохранение исходного состояния, журнал транзакции, поэтапная проверка и восстановление с сохранением незавершённого recovery snapshot при ошибке. Проверенная upstream-логика отката для этой задачи не подходит.
- Встроен выбор исходных шаблонов: 2 Mihomo YAML и 7 Xray JSON-фрагментов из `zxc-rv/assets`, ревизия `26e20e85ddde31622a7002e6567698c9389b164e`. Ресурсы проверены HTTP 200 и доступны по ссылкам из каталога. XKeen UI сохраняет собственную реализацию редактора; загрузка шаблона заменяет только локальный черновик.

## Что берём в собственную архитектуру

| Область | Подход XKeen UI |
|---|---|
| Mihomo selectors/connections | Отдельный адаптер Clash API с типизированными ответами и явным состоянием недоступности ядра |
| Mihomo DNS и Xray DNS | Два независимых модуля и отдельные проверки; не смешивать с системным DNS роутера |
| Конфигурации | TypeScript editor + Rust schema/semantic validation, staging, snapshot, atomic apply и rollback |
| Службы и ядра | Узкий allowlist операций, фиксированные executable/args, проверка checksum, dry-run и подтверждение |
| Backup | Rust API с безопасным корнем файлов, атомарной записью, ограничением размера и журналом без конфигурационных секретов |
| Авторизация | Обязательна до любого сетевого API управления; loopback по умолчанию для разработки |
| Установка | POSIX ash, явное подтверждение, target-aware release и SHA-256 до извлечения |

Ничего из списка выше не считается реализованным только на основании этого аудита. Фактический статус указан в `PLAN.md` и `PROJECT_STATUS.md`.
